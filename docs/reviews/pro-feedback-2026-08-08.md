> **과거 검토 원문:** 이후 사용자 결정으로 호출 정책, 자동 복귀, QR 확인과 시연 중심이 변경됐다. 현재 기준은 [반영 판정](pro-feedback-disposition-2026-08-08.md)과 [ADR-0004](../decisions/0004-service-policy.md)를 따른다.

아래 표기에서 **[확정]**은 첨부 문서 또는 공식 출처로 확인된 내용, **[가정]**은 현재 기획이 전제로 둔 내용, **[권고]**는 검토 결과 제안하는 변경안이다. 동일 사항에서 문서가 충돌하면 공통 규정이 우선한다는 조항을 기준으로 삼았다(`2026_rules.pdf`, p.7).

## 1. 네가 이해한 프로젝트

### 재구성한 프로젝트

**[확정]** 4인 팀이 병원 내부 이동을 보조하는 자율주행 휠체어의 **축소형 종단 시스템 프로토타입**을 개발한다. 실제 환자는 태우지 않고, 영유아보다 작은 인형이 탑승하는 모형을 사용한다.

시스템에는 두 가지 요청 진입점이 있다.

1. 환자가 지정 승차장에서 휠체어를 직접 호출한다.
2. 의료진이 환자의 이동 예정 시각, 승차 위치, 목적지를 미리 등록한다.

이를 하나의 운행 흐름으로 연결한다.

```text
환자 호출 또는 의료진 예약
→ 요청 가능 여부 판단
→ 한 대의 휠체어에 미션 배정
→ 대기 장소에서 지정 승차장으로 이동
→ 현장 탑승·출발 확인
→ 지정 경로를 따라 목적지로 이동
→ 장애물 발생 시 정지
→ 목적지 도착
→ 운행 종료
→ 선택적으로 대기 장소 복귀
```

### 이 프로젝트를 평가할 때의 정확한 정의

**[권고]** 이 작품은 다음처럼 정의해야 한다.

> “실제 환자 탑승형 의료 제품”이 아니라, 병원 예약 이동과 현장 호출을 하나의 운행 상태 모델로 연결하는 **축소형 병원 이동 모빌리티 운영 POC**.

축소 모형으로 검증할 수 있는 것은 다음이다.

* 호출·예약·배차·운행 상태의 연결
* 임베디드 구동 제어
* 고정 경로 주행
* 장애물 정지
* 통신·경로·배터리 실패 처리
* 관제 화면과 로봇 상태의 일치

반대로 검증할 수 없는 것은 다음이다.

* 성인 탑승 하중과 구조 안전
* 승차감과 전복 안정성
* 실제 병원 복도의 혼잡 대응
* 임상 환경의 안전성
* 실제 환자 대상 서비스 적합성
* 실환자 탑승 제품에 필요한 법규·인증 적합성

### 잘못 이해하기 쉬운 지점

| 항목            | 현재 오해 가능성      | 올바른 해석                                         |
| ------------- | -------------- | ---------------------------------------------- |
| 병원 지도가 존재함    | 지도가 있으면 주행 가능  | 지도와 로봇의 현재 위치 추정은 별개 문제다.                      |
| 관제용 위치가 불필요함  | 위치 추정 자체가 불필요  | 연속 좌표는 없어도 되지만, 로봇은 현재 노드·구간·다음 체크포인트를 알아야 한다. |
| 카메라가 장애물을 인식함 | 장애물 회피까지 해결    | 인식, 정지, 안전거리 판단, 우회 경로 생성은 각각 다른 문제다.          |

### 심각도순 문제

#### 1. 제출 마감과 현재 진행 상태가 충돌한다 — **치명적**

**[확정]** 자유공모는 2026년 9월 3일까지 참가신청서, 20페이지 이내 개발완료보고서, GitHub URL, 3분 이내 시연영상을 제출해야 한다(`2026_free_details.pdf`, pp.3–4). 개발완료보고서는 구현 환경, 프로그램 설명, 장애요인과 해결방안, 차별성, 기대효과, 일정과 업무분장까지 포함해야 한다(`2026_report_guide.pdf`, p.2).

현재가 2026년 8월 8일이므로 마감까지 26일이다. 공식 홈페이지도 자유공모의 팀 구성 및 개발완료보고서 제출 기간을 9월 3일까지로 안내하고 있다. ([ESW Contest][1])

**문제:** “결과물을 완성한 뒤 참가 신청한다”는 전략에는 이점이 없고, 제출 실패 위험만 높인다.

**[권고-MUST]**

* 참가 등록과 팀명 확정을 즉시 진행한다.
* 내부 제출 마감은 9월 2일로 둔다.
* 9월 3일은 제출 장애 대응용으로 남긴다.
* 8월 10일 이후에는 핵심 범위를 추가하지 않는다.

---

#### 2. 현재 범위는 4인·26일 일정에 비해 지나치게 크다 — **치명적**

현재 기획은 다음을 동시에 요구한다.

* 축소 휠체어 하드웨어
* 모터·전원·센서·통신 펌웨어
* 실내 자율주행
* 위치 추정
* 장애물 인식
* 국소 우회
* 환자 인터페이스
* 의료진 인터페이스
* 예약·호출·배차 서버
* 관제
* 자동 복귀
* 안전 기능
* 보고서·GitHub·영상

이는 하나의 학생 프로젝트가 아니라 여러 서브프로젝트의 묶음이다.

**[권고]** 이번 대회에서 반드시 제거해야 할 것은 범용 자율주행과 국소 우회다. 웹 화면을 줄이는 것보다 자율주행 범위를 줄이는 것이 일정 효과가 크다.

---

#### 3. 제시된 핵심 차별점 대부분이 이미 상용 선행 사례와 겹친다 — **매우 높음**

요코하마시립시민병원의 WHILL 서비스는 다음을 이미 제공한다.

* 기체의 터치패널에서 목적지 선택
* 지정된 승차장과 제한된 목적지
* 사람과 장애물 회피
* 하차 후 기체 자동 복귀 ([横浜市立市民病院][2])

WHILL의 공식 사업자용 서비스는 여기에 더해 다음도 설명한다.

* 업무 관리 플랫폼과의 실시간 배차 연동
* 요청을 가용 인력 또는 자율 장치에 배정
* 위치, 배터리, 가용 여부, 상태의 실시간 추적
* 외부 운영 플랫폼과의 통합 가능성 ([Whill][3])

따라서 다음 주장은 차별점으로 약하다.

* 앱과 로봇을 연결했다.
* 의료진이 배차한다.
* 관제 화면에서 위치와 상태를 본다.
* 목적지를 선택한다.
* 장애물을 피한다.
* 자동 복귀한다.

**[권고-MUST]** 차별화 초점을 다음으로 좁혀야 한다.

> 예약된 도착 목표시각을 기준으로 출발 시점을 계산하고, 예정 이동과 현장 직접 호출을 동일한 미션 상태 모델에서 충돌 없이 처리하며, 실패와 수동 회수까지 추적하는 축소형 운영 POC.

다만 WHILL에 해당 기능이 없다고 주장해서는 안 된다. 검토한 공개 자료에서 병원 환자 ID·진료 예약과 직접 연동하는 구체적 흐름이 확인되지 않았을 뿐이며, 이는 “부재 증명”이 아니다.

---

#### 4. 실제 환자용 제품과 인형 탑승 모형의 주장이 섞여 있다 — **매우 높음**

**[가정]** 대상 환자는 스스로 승하차가 가능하다.

그러나 현재 기획에는 다음이 없다.

* 탑승 가능 대상과 제외 대상
* 발과 옷이 바퀴에 걸리지 않는지 확인
* 승객이 완전히 앉았는지 확인
* 하차 완료 확인
* 보호자 또는 의료진 개입 조건
* 운행 중 승객이 정지를 요청하는 방식

실제 WHILL 사례도 독립적으로 일어나 이동 장치로 옮겨 탈 수 있는 사용자를 대상으로 하고, 추가 승차 보조가 필요한 사람은 기존 인력 서비스를 사용한다고 설명한다. ([Whill][4])

**[권고-MUST]** 대회 범위에서 사용자는 “인형”이고, 실제 서비스 가정은 “독립 승하차가 가능한 환자와 지정 승차장”으로 제한한다. 실제 환자 사용 가능성을 시연 결과로 주장하지 않는다.

---

#### 5. 시스템에서 누가 최종 권한을 가지는지가 정의되지 않았다 — **매우 높음**

현재는 앱, 서버, 로봇, 펌웨어가 존재하지만 다음이 불명확하다.

* 서버가 `운행 시작`을 명령했는데 로봇이 장애물을 발견하면 누가 우선하는가
* 통신이 끊겼을 때 기존 경로를 계속 갈 것인가
* 앱과 로봇의 상태가 다르면 어느 상태가 진실인가
* 중복 명령이 오면 어떻게 처리하는가
* 비상정지 해제 후 자동 재출발하는가

**[권고-MUST]**

* 서버: 요청, 예약, 대기열, 미션 배정의 권한
* 로봇 상위 제어: 미션 수행, 경로 진행, 로컬 안전의 권한
* 펌웨어: 모터 출력과 물리적 정지의 최종 권한
* 클라이언트: 요청과 표시만 담당

로봇의 장애물 정지와 비상정지는 서버보다 우선해야 한다.

---

#### 6. “지도는 있다”는 가정이 자율주행 방법의 결정을 미루게 한다 — **높음**

지도 파일이 있다고 해도 로봇이 현재 어느 위치와 방향에 있는지 모르면 경로를 실행할 수 없다.

**[권고-MUST]** 연속 좌표 기반 자율주행을 포기하고, 체크포인트와 경로 구간을 기준으로 하는 의미적 위치 체계를 사용한다.

```text
HOME
→ SEGMENT_HOME_PICKUP
→ PICKUP_A
→ SEGMENT_PICKUP_DEST
→ DESTINATION_B
```

이 정도면 배차, 주행 상태 표시, 경로 이탈 판단에 충분하다.

---

#### 7. 장애물 “정지”와 “우회”가 같은 기능처럼 취급된다 — **높음**

장애물 감지 후 멈추는 것은 비교적 단순하다. 장애물을 우회하려면 다음이 추가된다.

* 주변 자유공간 인식
* 로봇 폭과 회전 반경 반영
* 대체 경로 생성
* 원래 경로로 복귀
* 승객 안전을 고려한 속도와 방향 변화
* 우회 중 새로운 장애물 처리

**[권고-CUT]** 이번 대회에서는 우회를 제거하고, 장애물 지속 시 `BLOCKED` 상태로 전환한다.

---

#### 8. 한 대의 로봇에 두 종류의 요청을 넣으면서 충돌 규칙이 없다 — **높음**

환자 직접 호출과 예약 이동이 동시에 발생하면 다음을 결정해야 한다.

* 먼저 들어온 요청 우선인지
* 검사 예약 우선인지
* 이미 이동 중인 로봇을 재배정할 수 있는지
* 예약시각을 지킬 수 없는 요청을 받을 것인지
* 호출을 대기시킬 것인지 거절할 것인지

**[권고-MUST]** 복잡한 최적화 대신 한 가지 결정 규칙을 사용한다.

```text
한 번에 활성 미션은 1개
→ 기존 예약을 지킬 수 있는 경우에만 직접 호출 수락
→ 불가능하면 직접 호출은 대기 또는 거절
→ 운행 중인 미션은 재배정하지 않음
```

---

#### 9. 성공 기준이 없어 영상만 잘 나오면 완성된 것처럼 보일 위험이 있다 — **높음**

“한 번 성공했다”는 완성도 증거가 아니다.

**[권고-MUST]**

* 종단 운행 5회 연속 성공
* 장애물 정지 시험 5회 모두 무접촉
* 비상정지 시험 성공
* 통신 끊김 시험 성공
* 경로 상실 시험 성공
* 모든 시험에 시간과 결과 로그 남김

## 3. 대회 적합성과 차별성

### 자유공모 적합성

**[확정]** 자유공모는 자유로운 주제의 임베디드SW 개발을 대상으로 하며, 재료와 규격 제한은 없지만 다치기 쉬운 재료와 운반하기 어려운 크기는 피하도록 안내한다. 4인 팀도 1~5인 규정에 부합한다(`2026_free_details.pdf`, p.2).

따라서 주제와 팀 구성은 적합하다. 특히 실제로 움직이는 임베디드 장치와 서버·인터페이스가 연결되므로, 순수 웹 서비스보다 임베디드SW 적용성을 보여주기 쉽다.

다만 자유공모 예선은 아이디어 제안만 평가하지 않는다. 소스코드, 실제 시연영상, 구현 환경, 프로그램 구성, 장애요인과 해결방안까지 제출해야 한다(`2026_free_details.pdf`, pp.4–5; `2026_report_guide.pdf`, p.2).

### 독창성 주장을 안전하게 표현하는 방법

권장 표현:

> 본 작품은 자율주행 휠체어 자체의 최초성을 주장하지 않는다. 기존 목적지 선택형 자율 이동 서비스와 달리 보이려는 것이 아니라, 병원 예약의 도착 목표시각과 현장 호출을 하나의 미션 상태 모델로 연결하고, 한정된 로봇 자원에서 요청 충돌·장애물·통신 끊김·수동 회수까지 처리하는 종단 운영 구조를 축소형 임베디드 플랫폼으로 구현하고 검증하는 데 초점을 둔다.

피해야 할 표현:

* 국내 최초 자율 휠체어
* 병원 예약과 연동한 사례가 없다
* 기존 서비스는 단순 자율주행뿐이다
* 완전 자율주행
* 실제 병원에 바로 적용 가능
* 환자 안전이 보장된다

### 영상 신뢰도를 높이는 원칙

* 이동 구간은 가능한 한 한 화면의 연속 촬영으로 보여준다.
* 대기시간은 편집할 수 있지만, 출발·정지·장애물 대응 직전과 직후를 잘라 붙이지 않는다.
* 화면 한쪽에 로봇 상태를 오버레이한다.
* 외부에서 원격 조종하지 않았다는 점이 보이도록 조종기나 키보드를 프레임 밖에서 사용하지 않는다.
* 기능을 많이 나열하기보다 한 개의 미션이 처음부터 끝까지 닫히는 장면을 우선한다.

### 관제용 실시간 위치와 로봇 내부 위치 추정의 차이

* 승차장으로 가는 중인지
* 어느 구간에 있는지
* 장애물로 멈췄는지
* 목적지에 도착했는지

이 목적에는 정밀한 `x, y, θ` 좌표가 필수적이지 않다.

```text
현재 위치: PICKUP–DEST 구간
진행률: 약 60%
상태: BLOCKED
다음 체크포인트: CP-04
```

정도로 충분하다.

#### 로봇 내부 위치 추정

로봇이 다음 행동을 결정하기 위한 정보다.

* 지금 어떤 경로 구간을 따라가는지
* 어느 방향으로 진행하는지
* 다음 체크포인트가 무엇인지
* 예정된 체크포인트를 놓쳤는지
* 목적지 정지 조건을 충족했는지

이는 관제 화면보다 높은 주기와 신뢰도로 로컬에서 처리해야 한다. 서버 통신에 의존해서는 안 된다.

### 축소 프로토타입의 최소 위치·경로 인식 수준

**[권고-MUST]** 다음 정보면 충분하다.

```text
current_node
current_edge
direction
next_checkpoint
path_confidence
estimated_progress
mission_state
stop_reason
```

연속 좌표 대신 경로 그래프와 체크포인트 순서를 사용한다.

### 가능한 방식 비교

| 방식                     | 필요한 조건                        | 장점                 | 단점                              | 현재 적합성          |
| ---------------------- | ----------------------------- | ------------------ | ------------------------------- | --------------- |
| LiDAR·비전 SLAM 기반 연속 좌표 | 지도, 연산 장치, 센서 보정, 환경 특징, 경로계획 | 자유로운 경로와 높은 확장성    | 통합·보정·드리프트·동적 환경 위험             | 낮음              |
| 외부 천장 카메라 기반 위치        | 고정 카메라, 좌표 보정, 시야 확보          | 시연용 좌표 표시가 쉬움      | 외부 인프라 의존, 가림에 취약, 로봇 자체성이 낮음   | 관제 보조용으로만 선택 가능 |
| 체크포인트 기반               | 노드 마커, 노드 사이 이동 방식            | 상태가 명확하고 실패 판정이 쉬움 | 위치가 이산적이며 인프라 필요                | 높음              |
| 라인·마커 기반               | 바닥 경로, 하향 경로 센서, 역·교차점 마커     | 가장 빠르고 반복성이 높음     | 일반 환경 확장성 낮고 단순 라인트레이서로 보일 수 있음 | 가장 높음           |
| 엔코더 데드레커닝만 사용          | 일정한 바닥, 정확한 바퀴, 짧은 거리         | 구현이 단순함            | 미끄러짐과 누적 오차에 취약                 | 단독 사용 비권장       |

### 현재 팀과 일정에 가장 적합한 기본안

**[권고-MUST]**

> 바닥 경로 가이드 + 역·교차점 체크포인트 + 구간별 의미적 상태 + 짧은 구간의 엔코더 진행량.

구체적인 구성 원칙은 다음과 같다.

1. **경로 유지 요구사항**
   로봇은 정해진 평면 경로에서 중심 오차를 보정해야 한다.
   센서 후보는 하향 반사형 경로 센서 배열 또는 하향 카메라다.
   경험이 없다면 반사형 경로 센서가 더 단순하고 조명 변화에 덜 민감하다.

2. **체크포인트 요구사항**
   승차장, 목적지, 교차점과 대기 위치를 확실히 구분해야 한다.
   광학 마커, 색상 마커, 기하학 마커 중 팀이 안정적으로 판독할 수 있는 것을 사용한다.

3. **진행량 요구사항**
   체크포인트 사이에서 비정상적으로 오래 이동하거나 멈추지 않는 문제를 잡아야 한다.
   바퀴 엔코더는 속도 제어, 진행량 추정, 제동거리 측정에 유용하다.

4. **장애물 안전 요구사항**
   장애물 종류를 분류하는 것보다 충돌 전에 정지하는 것이 우선이다.
   전방 거리 감지는 카메라 인식과 독립된 결정론적 센서가 맡는 것이 낫다.

5. **카메라 사용 조건**
   이미 카메라 처리 경험이 있고 하드웨어가 준비된 경우에만 장애물 종류 표시나 시연 영상 기록에 사용한다. 안전 정지를 카메라 모델 하나에 맡기지 않는다.

### 라인 기반이 지나치게 단순해 보이지 않게 하는 방법

* 미션 상태에 따라 서로 다른 다음 체크포인트를 선택한다.
* 체크포인트 누락 시 정지한다.
* 장애물 상태와 통신 실패를 로컬에서 처리한다.
* 서버의 미션과 로봇의 물리 상태를 일치시킨다.
* 반복 시험 결과와 제동거리 근거를 제시한다.

기술성은 센서 종류의 화려함보다 **상태 제어, 실패 처리, 반복성**에서 확보하는 편이 낫다.

| `firmware/`   | 유지       | 모터 제어, 경로 센서, 거리 센서, 비상정지, 하트비트와 저수준 상태를 담당한다.                                   |
| `hardware/`   | 유지       | 회로, 기구, 전원, 조립과 안전 관련 문서가 들어가는 비실행 영역이다.                                         |
| `contracts/`  | 유지하되 최소화 | 미션 명령, 상태, 오류 코드, 지도 노드 규격만 둔다. 독립된 거대한 공용 라이브러리로 만들지 않는다.                       |
| `data/`       | 유지       | 경로 그래프, 가상 병원 데이터, 시험 결과를 둔다. 실제 환자 정보는 넣지 않는다.                                  |
| `simulation/` | 축소       | 정교한 물리 시뮬레이터는 필요 없다. 서버 개발용 가짜 로봇 어댑터 또는 상태 재생기만 있으면 된다.                         |
| `tests/`      | 반드시 유지   | 미션 상태 전이, 통신 끊김, 경로 상실, 장애물 정지, 종단 시험을 둔다.                                       |
| `demo/`       | 유지       | 촬영 순서, 실패 복구 절차, 성공 기준과 증거 파일을 둔다.                                               |

### 가장 중요한 권한 경계

```text
클라이언트
  요청 생성·상태 표시
        ↓
서버
  예약·대기열·배정·미션 상태 이력
        ↓
로봇 상위 제어
  경로 진행·체크포인트·로컬 안전·명령 거부
        ↓
펌웨어
  센서 입력·모터 출력·물리 정지
```

다음 원칙을 고정해야 한다.

* 클라이언트는 미션 상태를 임의로 완료 처리하지 않는다.
* 서버는 로봇의 물리 안전 정지를 해제할 수 없다.
* 로봇은 오래되거나 다른 미션 ID의 명령을 거부한다.
* 펌웨어는 통신이 끊겨도 비상정지와 장애물 정지를 수행한다.
* 비상정지 해제 후 자동 재출발하지 않는다.

### 빠진 것은 새 디렉터리가 아니라 명확한 모델이다

필요한 핵심 상태는 다음 정도다.

```text
QUEUED
ASSIGNED
TO_PICKUP
WAIT_BOARDING
TO_DESTINATION
ARRIVED
COMPLETED

BLOCKED
E_STOP
COMMS_LOST
PATH_LOST
LOW_BATTERY
RECOVERY_REQUIRED
```

`contracts/`의 핵심은 파일 수가 아니라 이 상태와 전이 규칙이다.

### 불필요한 복잡성

다음은 권하지 않는다.

* 마이크로서비스
* 메시지 브로커 필수화
* Kubernetes·컨테이너 오케스트레이션
* 환자 앱과 의료진 앱의 별도 백엔드
* 클라우드가 없으면 동작하지 않는 구조
* 여러 로봇을 전제로 한 범용 플릿 플랫폼

| P1   | 오래된·중복 명령     | 명령 무시, 기존 안전 상태 유지          | 미션 ID와 시퀀스 재동기화               | 해당 없음 |
| P2   | 수동 회수         | 모터 출력 차단, 현재 미션 실패 처리       | 모형을 들어 옮기거나 구동을 해제하고 이동       | 금지    |

### 비상정지

**[권고-MUST]**

* 앱의 정지 버튼은 보조 수단이다.
* 실제 물리 버튼이 있어야 한다.
* 가능하면 메인 애플리케이션이 멈춰도 모터 구동 허가를 끊을 수 있어야 한다.
* 눌렀다 놓는 즉시 다시 움직이는 구조는 피한다.
* 리셋 후에도 새로운 출발 확인이 필요하다.

### 통신 끊김

대회용 로봇이 경로를 로컬에 가지고 있더라도, 이번 범위에서는 통신 끊김 후 계속 운행하는 것보다 정지가 낫다. 계속 운행은 복구와 서버 상태 일치를 더 어렵게 만든다.

### 장애물 지속

다음과 같이 단순화한다.

```text
장애물 감지
→ 정지
→ BLOCKED
→ 운영자 알림
→ 장애물 제거
→ 현장 재개 확인
→ 운행 재개
```

우회, 후진 탐색, 경로 이탈은 하지 않는다.

### 경로 이탈

라인을 잃었을 때 좌우로 크게 흔들며 경로를 찾는 동작은 시연 실패뿐 아니라 충돌 위험을 높인다. 짧은 보정 범위를 넘으면 즉시 정지해야 한다.

### 배터리

* 운행 전 배터리 상태 확인
* 낮은 배터리에서는 새 미션 거부
* 운행 중 임계 저하 시 정지와 회수
* 배터리 값이 비정상적이거나 읽히지 않아도 정상으로 간주하지 않음

### 수동 회수

대회용 모형에서 별도의 원격 조종 기능까지 만들 필요는 없다.

**[권고]** 비상정지 후 모터 출력을 끄고, 사람이 모형을 들어 안전 구역으로 옮기는 절차면 충분하다. 수동 회수 사실은 미션 로그에 `RECOVERY_REQUIRED` 또는 `ABORTED`로 남긴다.

### 실제 환자용 제품과의 경계

위 정책은 축소 모형의 기본 안전조치다. 실제 환자용 제품에는 승객 구속, 발판과 바퀴 간 간섭, 기계 브레이크, 전복, 경사로, 단차, 계단, 화재·배터리, 전자파, 다중 센서 고장 등 별도의 안전 프로그램이 필요하다. 이번 결과물로 이를 검증했다고 표현해서는 안 된다.

## 9. 4인 팀 실행 가능성

### 권장 병렬 작업 경계

| 담당          | 주 업무                                    | 통합 산출물                   |
| ----------- | --------------------------------------- | ------------------------ |
| 임베디드·하드웨어 A | 차체, 구동계, 전원, 배터리, 물리 비상정지, 기구 안전        | 안정적으로 움직이고 즉시 정지하는 플랫폼   |
| 임베디드·하드웨어 B | 모터 제어, 경로 센서, 체크포인트, 장애물 센서, 하트비트       | 로컬 주행·정지·오류 상태를 제공하는 펌웨어 |
| 소프트웨어 A     | 경로 그래프, 미션 실행기, 로봇 상태 머신, 서버 통신, 통합 책임  | 서버 명령을 실제 로봇 행동으로 변환     |
| 소프트웨어 B     | 단일 웹 클라이언트, 예약·호출·배차 서버, 이벤트 로그, 보고서 취합 | 미션 생성부터 완료까지의 운영 흐름      |

`contracts/`는 소프트웨어 A가 주 소유자가 되고, 임베디드 B와 소프트웨어 B가 함께 승인하는 방식이 적절하다.

### 통합 순서

1. **물리 정지부터 검증**
   모터 구동, 저속 제어, 비상정지, 전원 안정성.

2. **서버 없이 한 구간 주행**
   라인 유지, 체크포인트 정지, 장애물 정지.

3. **가짜 로봇으로 서버·웹 완성**
   실제 하드웨어를 기다리지 않고 미션 상태를 검증.

4. **로봇 상위 제어와 펌웨어 연결**
   `MOVE_TO`, `STOP`, 상태·오류 메시지.

5. **서버와 실제 로봇 연결**
   하나의 미션을 대기 장소부터 목적지까지 수행.

6. **실패 처리 연결**
   장애물, 통신 끊김, 경로 상실, 비상정지.

7. **반복 시험과 촬영**
   기능 추가를 중단하고 안정화한다.

### 가장 위험한 의존성

1. 차체와 모터가 늦게 준비되는 것
2. 전원 노이즈나 전압 저하로 제어 보드가 재부팅되는 것
3. `contracts/`가 계속 바뀌어 서버와 로봇이 서로 기다리는 것
4. 라인·마커 인식이 조명과 바닥에 따라 달라지는 것
5. 웹 팀이 실제 로봇이 올 때까지 통합을 미루는 것

## 10. 수정된 기획 v0

### 작품 정의

**작품명 예시**

> 병원 예약 연동형 이동 보조 모빌리티 운영 POC

### 해결하려는 문제

거동이 불편하지만 독립적으로 승하차 가능한 환자가 예약된 검사나 진료 장소로 이동할 때, 의료진이 직접 휠체어를 운반하거나 이동 시각을 반복 확인해야 하는 부담이 발생한다고 가정한다.

### 대상 사용자

* **직접 사용자:** 독립 승하차가 가능한 환자를 모사한 인형
* **운영 사용자:** 예약과 이동 상태를 관리하는 의료진
* **제외 대상:** 승하차 보조가 필요한 환자, 응급환자, 실제 환자

### 운영 환경

* 한 층의 평면 모형 병원
* 한 대의 축소 모빌리티
* 대기 위치 1개
* 지정 승차장 1개
* 목적지 1개
* 고정된 인프라 보조 경로

### 사용자 흐름

```text
의료진이 가상 환자 P-001의
목표 도착시각·승차장·목적지 등록
→ 서버가 예상 이동시간과 탑승 버퍼 계산
→ 출발 가능 시각에 미션 생성
→ 로봇이 대기 위치에서 승차장으로 이동
→ 인형 탑승
→ 현장 출발 버튼
→ 목적지 이동
→ 장애물 발견 시 정지 및 BLOCKED
→ 장애물 제거와 재개 확인
→ 목적지 도착
→ 미션 완료
→ 선택적으로 대기 위치 복귀
```

승차장 직접 호출은 같은 미션 파이프라인에 들어가며, 기존 예약을 지킬 수 있을 때만 수락한다.

### 자율주행 방식

**[변경]** 범용 지도 기반 자율주행에서 인프라 보조형 체크포인트 주행으로 변경한다.

* 바닥 경로 가이드
* 승차장·목적지·교차점 마커
* 구간 진행량 추정
* 장애물 시 정지
* 경로 누락 시 정지
* 국소 우회 없음

**변경 이유:** 26일 안에 반복 신뢰도를 확보하고, 실패 판정을 명확히 하기 위해서다.

### 사용자 인터페이스

**[변경]** 환자용 PWA와 의료진용 웹을 별도 제품으로 만들지 않는다.

하나의 반응형 웹 앱에서 다음 화면만 제공한다.

* 의료진 예약 등록 화면
* 승차장 직접 호출 화면
* 미션 대기열
* 로봇의 의미적 위치와 상태
* 실패·회수 로그

**변경 이유:** 별도 앱은 기술 점수보다 개발·통합 비용이 크다.

### 배차 로직

**[추가-MUST]**

```text
release_at =
목표 도착시각
- 대기 위치→승차장 예상시간
- 탑승 버퍼
- 승차장→목적지 예상시간
```

한 대의 로봇이 이미 미션을 수행 중이거나 기존 예약과 충돌하면 새 직접 호출은 대기 또는 거절한다. 운행 중인 미션의 목적지를 변경하지 않는다.

**추가 이유:** 단순한 호출 앱과 차별화하고 의료진 예약 흐름을 실제 운영 로직으로 만들기 위해서다.

### 안전

* 물리 비상정지
* 현장 출발 확인
* 장애물 로컬 정지
* 통신 끊김 정지
* 경로 상실 정지
* 배터리 낮음 미션 거부
* 자동 재출발 금지
* 수동 회수 절차
* 실제 사람 탑승 금지

### 관제

**[변경]** 연속 좌표 지도 대신 의미적 상태를 표시한다.

```text
위치: PICKUP–DEST 구간
상태: BLOCKED
다음 체크포인트: CP-04
배터리: LOW/NORMAL
미션: M-002
```

**변경 이유:** 현재 시스템에서 정밀 좌표는 배차나 안전에 필수적이지 않다.

### 자동 복귀

**[변경]** 필수 기능에서 선택 기능으로 내린다.

**변경 이유:** 상용 선행 사례와 겹치며, 운행 성공과 장애물 정지가 자동 복귀보다 점수 기여도가 높다.

### 성공 지표

* 예약 등록부터 운행 완료까지 5회 연속 성공
* 승차장·목적지 정지 구역 진입 성공
* 장애물 시험 5회 모두 무접촉 정지
* 비상정지 후 자동 재출발 없음
* 통신 끊김 시 정지
* 잘못된 체크포인트 또는 경로 상실 시 정지
* 서버·로봇·영상에 동일 미션 ID 표시

### 공식적인 차별화 문장

> 본 작품은 자율주행 휠체어 자체의 최초성을 주장하지 않으며, 예약 목표시각 기반 선제 배차와 현장 호출을 하나의 미션 상태 모델로 통합하고, 장애물·통신·경로·배터리 실패와 수동 회수까지 포함한 종단 운영 구조를 축소형 임베디드 모빌리티에서 구현하고 검증한다.

## 12. 최종 판정

### 현재 상태에서 진행할 가치가 있는가

**조건부로 있다.**

병원 이동 보조라는 문제는 활용성이 있고, 임베디드 구동·서버·웹·안전 상태를 연결하면 대회에 적합한 종단 작품이 될 수 있다. 그러나 현재의 “자율주행 휠체어 전체 시스템” 범위 그대로는 일정과 차별성 모두 불리하다.

진행 조건은 다음과 같다.

* 범용 자율주행을 포기한다.
* 국소 우회를 제거한다.
* 실제 환자용 제품 주장을 제거한다.
* 예약 목표시각 기반 운영 로직을 중심으로 삼는다.
* 8월 22일까지 첫 종단 운행을 성공시킨다.

### 가장 먼저 확정해야 할 한 가지

> 작품의 본질을 “자율 휠체어”가 아니라 “예약 목표시각 기반 병원 이동 모빌리티 운영 POC”로 확정하는 것.

이 결정이 주행 방식, 앱 범위, 보고서의 차별성, 시연 순서를 모두 결정한다.

행정적으로는 참가 등록을 즉시 진행해야 한다.

### 가장 먼저 검증해야 할 한 가지

> 물리 비상정지가 있는 축소 차량이 경로 한 구간을 스스로 따라가고, 장애물 앞에서 무접촉 정지하는지.

앱이나 예약 서버보다 먼저 검증해야 한다. 이것이 실패하면 전체 시스템의 전제가 무너진다.

### 이번 대회에서 절대 욕심내지 말아야 할 한 가지

> SLAM과 동적 장애물 국소 우회.

둘 중 하나만 시도해도 일정이 크게 흔들릴 수 있으며, 둘을 함께 시도하면 종단 완성도와 제출물 품질이 희생될 가능성이 높다.

### 판정에 대한 확신도와 불확실성
