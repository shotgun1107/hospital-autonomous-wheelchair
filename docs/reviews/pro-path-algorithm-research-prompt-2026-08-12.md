# Pro 검토 요청 — 자율휠체어 경로 알고리즘 재검토와 다음 실험 방향

## 1. 요청 목적

병원 자율주행 휠체어의 축소 시뮬레이션 연구에서 전역 경로 탐색부터 동적 장애물 대응까지 여러 방식을 구현하고 시험했다. 정적 경로 탐색과 기본 추종은 동작하지만, 느리게 같은 방향으로 움직이는 사람을 안전하게 옆으로 우회하고 다시 원 경로에 합류하는 동적 장면은 아직 완성하지 못했다.

이 문서를 바탕으로 다음을 검토해 달라.

> 먼저 문헌을 폭넓게 조사해서 유용할 만한 결과를 찾되, 이동 로봇 분야에만 스스로를 한정하지 말 것. 자율주행차, 창고 AMR, 보조공학·스마트 휠체어, 군중 내비게이션, 게임·그래프 탐색, 최적제어, 런타임 안전 보증 등 인접 분야도 조사할 것.

이번 요청은 제품 알고리즘의 최종 채택 요청이 아니다. 현재 증거를 비판적으로 검토하고, 어떤 구조와 실험을 다음에 검증해야 하는지 조건부로 추천하는 것이 목적이다.

## 2. 프로젝트와 증거의 한계

- 알려진 지도와 등록 지점을 사용하는 단층 통제 공간을 전제로 한다.
- 한 대의 축소 휠체어와 인형 탑승 시연을 대상으로 한다.
- 장애물 대응의 상위 원칙은 `먼저 정지 → 현재 정보로 안전한 대체 이동 판단 → 불가능하거나 불확실하면 정지 유지`다.
- 경로 알고리즘은 물리 비상정지나 하위 안전정지를 직접 해제하지 않는다.
- Python 시뮬레이션과 합성 지도 결과는 논리·기능 연구 증거일 뿐, 실제 사람 탑승 안전이나 의료기기·제품 인증의 증거가 아니다.
- 제품 범위의 `G1~G5`—시연 지도, 차체·제어 특성, 관측 정보, 실행·통신 경계, MVP 증거 범위—는 아직 팀 합의 전이다.
- 따라서 전체 경로 재선택, 제한적 현재 경로 수정, 두 기능의 조합은 모두 최종 채택되지 않은 상태다.

## 3. 현재까지 구현한 구조

각 알고리즘은 서로 다른 역할을 맡는다. 아래 항목을 하나의 알고리즘으로 합쳐 평가하지 말아 달라.

### 3.1 전역·정적 경로

- `Dijkstra`: 최단 경로 기준선과 독립 비교용 oracle.
- `A*`: 알려진 지도에서 출발지부터 목적지까지의 전역 경로 탐색.
- `D* Lite`: 지도 구간 상태가 바뀐 경우의 전역 경로 갱신 실험.
- `bounded Grid A*`: 현재 주변의 제한된 격자에서 차체 외곽과 금지구역을 반영한 지역 경로 생성 실험.

### 3.2 경로 추종

- `Pure Pursuit(PP)`: 주어진 경로를 따라가는 기준선.
- `Regulated Pure Pursuit(RPP)`: 곡률·장애물 조건에 따라 속도를 조절하며 주어진 경로를 추종하는 비교 후보.

PP와 RPP는 기본적으로 경로 추종기다. 스스로 장애물 옆의 새로운 우회 경로를 만드는 기능으로 간주하지 않는다.

### 3.3 국소 속도·궤적 선택

- 자체 구현 `DWA`: 현재 속도에서 가능한 속도 후보를 샘플링하고 짧은 미래 궤적을 평가한다.
- 소스 기반 `DWB Python reference`: ROS1 DWA와 Nav2 DWB의 공개 구현·문서를 기준으로 critic 구조를 재현한 연구용 Python 기준선이다.

DWA/DWB도 기본적으로 주어진 기준 경로와 목표에 대해 짧은 구간의 속도·궤적을 고르는 방식이다. 장애물 주변의 의미 있는 우회 경로 자체가 입력되지 않으면 정지나 감속을 선택할 수 있다.

### 3.4 동적 장애물 관측·예측·안전

- 10 Hz Actor 관측, 지연·잡음·dropout, TTL을 분리해 모델링했다.
- 관측 ground truth를 controller에 직접 제공하지 않는다.
- 20-frame 방향성 Actor 예측을 추가했다.
- controller 결과와 별도로 shared safety gate가 명령을 재검사한다.
- 실제 정지 완료, 입력 최신성, 재출발 허가를 분리한다.

## 4. 처음 의도한 경로 처리 방식

초기 의도는 다음과 같았다.

1. A* 또는 D* Lite가 전역 통로·경로를 정한다.
2. bounded Grid A*가 필요하면 현재 주변에서 제한적 우회 경로를 만든다.
3. PP/RPP 또는 DWA/DWB가 그 경로를 실제로 따라갈 속도 명령을 만든다.
4. 별도 안전 계층이 모든 명령을 다시 검사하고, 불확실하면 정지시킨다.

그러나 실제 동적 실험의 상당 부분에서는 2번의 명시적 지역 경로 생성 없이, 곧은 전역 기준 경로를 DWA/DWB에 주고 사람을 옆으로 피해 갈 수 있는지 먼저 시험했다. 여기서 구조적인 한계와 구현상의 문제가 함께 나타났다.

## 5. 자체 DWA에서 나타난 문제

### 5.1 동결한 실험 계약

- 속도 후보: 최대 217개
- rollout: 2.0초
- 시간 간격: 0.05초
- 후보당 pose: 41개
- terminal stopping 검사 포함
- 동적 실험에서는 후진 후보 제외
- Actor 표면 기준 여유: 0.08m
- 최종 명령은 독립 shared safety gate가 재검사

이 수치와 안전 기준을 결과에 맞춰 느슨하게 바꾸지 않았다.

### 5.2 `final-v4` 결과

- 공개 144회와 당시 hidden 120회를 실행했다.
- 전체 pipeline의 hard-safety 검사는 264/264 통과했다.
- 그러나 DWA 기능 성공은 hidden Normal 16/30, Stress 5/30이었다.
- 우회 가능으로 분류된 장면의 의미 있는 이탈·재합류 성공률은 0%였다.
- 최대 측면 이탈은 약 0.00585m에 그쳤다.
- 50ms 제한은 400회 중 324회 초과했다.

이 결과는 `DWA라는 알고리즘 계열 전체가 사용할 수 없다`는 증거가 아니다. 당시 Python 구현, 후보 생성 방식, 예측 모델, 기준 경로, critic·비용 구조와 실험 계약을 합친 특정 구현의 실패 자료다.

### 5.3 확인된 문제

1. 공개 기능·시간 자격을 통과하기 전에 hidden을 소비했다.
2. 모든 후보가 왜 탈락했는지 충분한 분류 기록이 없었다.
3. `우회 가능` 시나리오가 실제 차체 동역학으로 우회 가능한지 독립적으로 증명하지 못했다.
4. 정지 뒤 다시 출발할 때 허용되는 각속도 범위가 작아, 충분히 옆으로 틀기 전에 다시 멈추는 현상이 의심됐다.
5. 곧은 기준 경로를 유지하는 비용이 강해 안전한 회전 후보가 있어도 감속·정지를 선호했다.
6. 기존 원형 Actor 예측이 느린 사람도 모든 방향으로 갑자기 움직일 수 있다고 보수적으로 팽창시켜, 후보를 지나치게 많이 제거했다.

## 6. DWA 문제를 어떻게 보완했는가

### 6.1 실험·검증 구조 보완

- 후보 탈락 이유를 단계와 원인별로 기록하도록 했다.
- 공개 기능·안전·50ms 자격 전에는 새 hidden을 생성하지 못하도록 분리했다.
- 평가기의 운동학, 정지 epoch, 재출발 권한, 시간·상태 연속성 검사를 강화했다.
- 같은 seed와 외부 관측을 PP와 DWA가 공유하는 paired 실행 구조를 유지했다.
- 기존 직선 횡단뿐 아니라 같은 방향, 정면 접근, 대각선, 코너·교차로, 세로 경로와 다중 Actor 장면을 공개 corpus에 추가했다.

### 6.2 동작 보존형 속도 최적화

후보 수, pose 수, rollout, 비용, tie-break, terminal stopping과 외부 안전 gate를 바꾸지 않고 계산 중복을 줄였다.

- 정적 장애물 거리 계산 캐시·distance field
- 금지구역에 대한 보수적인 빠른 검사
- Actor tube 반복 샘플링과 기하 계산 축소
- 선택 결과가 달라지지 않는지 semantic digest로 전후 비교
- 경계 사례에서는 기존 정밀 검사로 되돌아가는 fallback

C++ DWA core의 별도 시간 시험에서는 500회 중 50ms 초과 0회, p50 약 3.77ms, p95 약 15.46ms, 최대 약 35.58ms를 기록했다. 하지만 기능적 우회는 여전히 실패했다. 즉 속도 문제 일부는 해결했지만 행동 문제는 해결하지 못했다.

## 7. DWB 기준 구현과 다시 확인한 문제

ROS1 navigation의 DWA와 Nav2 DWB 공개 소스·문서를 기준으로 연구용 Python reference를 만들었다.

포함한 요소:

- dynamic window와 trajectory generator
- critic lifecycle: `prepare → score → debrief → reset`
- PathDist, GoalDist, PathAlign, GoalAlign
- Oscillation, RotateToGoal
- 결정론적 tie-break
- 목표 부근 정지·회전 상태
- hard-constraint critic
- 외부 shared safety gate

이 구현은 Nav2 plugin이나 제품 controller가 아니라 알고리즘 동작을 분리해 확인하기 위한 느린 Python 기준선이다.

초기 같은 방향 장면에서는 217개 후보 전부가 Actor clearance 때문에 거부됐다. 원인은 DWB 자체만이 아니라 기존 Actor 예측 모델에도 있었다.

## 8. Actor 예측을 어떻게 바꿨는가

### 8.1 기존 문제

기존 원형 reachable model은 느리게 앞서가는 사람도 관측 직후 즉시 정지하거나 옆으로 움직이거나 반대 방향으로 갈 수 있다고 가정했다. 시간이 늘어날수록 원이 모든 방향으로 팽창해, 실제 같은 방향 장면의 옆 공간까지 막았다.

### 8.2 방향성 Capsule 모델

다음 연구용 모델을 추가했다.

1. 10 Hz 검증 관측에서 20개의 고유 frame을 모은다.
2. 평균 속도로 진행 방향과 신뢰도를 계산한다.
3. 단기적으로 진행 방향의 즉시 반전을 허용하지 않는 종방향 reachable interval을 만든다.
4. 횡방향 불확실성과 Actor 반경을 결합해 방향성 Capsule을 만든다.

같은 방향 공개 장면의 Normal 조건에서 READY가 된 첫 시점에는 217개 중 52개가 legal이었다. 66-tick 부분 실행에서는 tick 62에 재허가되고 4 tick 동안 실제 이동이 발생했다. 그러나 측면 이탈은 거의 없었다.

Stress 조건은 잡음과 낮은 속도 때문에 방향 신뢰도가 충분히 쌓이지 않아 계속 fail-closed로 닫히는 경향이 남았다.

## 9. 최신 집 로컬 실험 — 아직 미커밋 상태

다음 결과는 회사 정본 커밋 이후 집 PC에서 수행한 탐색 작업이다. 아직 전체 회귀, 문서 반영, commit과 push를 끝내지 않았으므로 확정 산출물과 구분해 검토해 달라.

### 9.1 관측 영향 분리

기존 Normal 설정은 그대로 두고 기능 원인 분리를 위한 두 프로필을 별도로 만들었다.

- `FUNCTIONAL_NO_DROPOUT`: Normal의 지연·잡음은 유지하고 dropout만 0.
- `FUNCTIONAL_IDEAL`: Normal 지연은 유지하고 잡음과 dropout을 0.

No-dropout 220-tick 실행 결과:

- 약 639초 소요
- 이동 42 tick
- 최대 측면 이탈 약 0.0048619m
- 추월·재합류·완료 없음

frame dropout이 없어도 Normal 잡음 때문에 방향 신뢰도가 반복적으로 초기화되어, 충분한 이동 시간이 만들어지지 않았다.

### 9.2 이상적인 관측에서도 나타난 critic 문제

Ideal 입력과 원래의 곧은 기준 경로를 사용했을 때:

- 안전한 회전 후보는 존재했다.
- 약 45개의 legal 후보가 나온 시점도 있었다.
- 하지만 Path·Goal 관련 critic이 옆으로 도는 후보보다 직진·감속·정지를 선택했다.
- 단순히 Actor에서 멀어질수록 보상하는 비용을 넣어 보았지만, 옆으로 우회하기보다 뒤에서 감속하는 행동을 강화했다. 이 실험은 채택하지 않았다.

### 9.3 외부 지역 우회 경로 정책 추가

DWB 내부 critic을 계속 변형하는 대신, 지역 우회 경로 생성과 속도 제어를 분리했다.

연구용 `DirectionalLocalDetourPolicy`가 다음을 수행한다.

- label을 받지 않고 방향성 Actor 예측, 지도, 현재 로봇 상태와 원래 기준 경로만 사용한다.
- 좌우 공간을 기존 충돌·금지구역 검사로 확인한다.
- `현재 위치 → 옆 지점 → Actor 앞 통과 지점 → 원 경로 재합류 → 원래 목적지`의 직사각형 형태 지역 reference를 만든다.
- DWB core, 217개 후보, 41개 pose, terminal stopping, Actor safety와 shared gate는 바꾸지 않는다.

처음에는 전체 우회 reference를 한 번에 DWB에 줬다. DWB는 회전은 했지만 전진하지 않았다. GoalAlign만 제거하거나 GoalDist까지 제거해도 각각 최종 목표 선호와 정지 tie 문제가 남았다. 대각선 진입도 해결하지 못했다.

### 9.4 최신 해결 방식: 다음 waypoint만 DWB에 제공

외부 정책은 전체 우회 경로를 유지하되, DWB에는 현재 수행해야 할 한 구간의 다음 waypoint만 제공하도록 바꿨다.

- 현재 위치 → 옆 지점
- 옆 지점 → Actor 앞 통과 지점
- 통과 지점 → 원 경로 재합류 지점
- 재합류 지점 → 원래 목적지

waypoint가 바뀔 때 새 DWB instance를 만들어 기존 goal-latch 계약을 억지로 깨지 않도록 했다.

Ideal 입력으로 공개 `same-direction-wide-r00`을 episode 시작부터 180 tick 연속 실행한 결과:

- 총 계산 시간: 약 891.37초
- 최초 실제 전진 명령 적용: tick 77
- 최대 적용 선속도: 약 0.153125m/s
- 마지막 pose: x≈0.631029, y≈2.098274, yaw≈−1.569707
- 원 경로 y=2.32
- 최대 원 경로 이탈: 0.221726m
- hard-safety 통과
- no-safe-candidate: 0회
- shared gate override: 20회
- 충돌·금지구역 진입 없음
- 종료 시 waypoint 1 수행 중
- 추월: 미달
- 재합류: 미달
- 목적지 도착: 미달

따라서 실제로 0.10m를 넘는 지역 경로 이탈은 처음으로 증명했다. 그러나 `이탈 → Actor 추월 → 일정 시간 재합류 유지 → 목적지 도착` 전체 순서는 아직 증명하지 못했다.

### 9.5 장시간 실행을 위한 checkpoint 탐색

순수 Python DWB가 tick당 약 6~7초 걸려 장시간 연속 실행이 어렵기 때문에 simulator에 시작 tick과 상태를 넘기는 checkpoint/resume 실험을 추가했다.

- 한 tick 재개에서 pose, 속도와 waypoint 상태는 이어졌다.
- 하지만 기존 evaluator는 episode 초기 상태부터 시작한 연속 기록만 안전 증거로 인정하므로, 중간 segment만 평가하면 provenance 오류가 난다.
- 따라서 재개 실행은 기능 탐색 자료로만 표시하고, 연속 hard-safety 증거로 사용하지 않도록 했다.
- 180→300 tick 실행은 시작했지만 사용자의 중단 지시에 따라 종료했다.
- 현재 실행 중인 프로세스는 없다.

checkpoint/resume 설계는 아직 탐색 단계이며, 안전 증거를 훼손하지 않는 정식 분할 평가 방식이 필요하다.

### 9.6 최신 검증 상태

- 이전 회사 정본에서는 전체 549개 회귀시험과 Ruff가 통과했다.
- 최신 집 로컬 변경 이후에는 집중 시험 118개, 지역 정책 5개, 시뮬레이션·안전 영향권 32개 등이 통과했다.
- 최신 미커밋 변경에 대해 전체 549개 회귀는 아직 다시 실행하지 않았다.
- 최신 변경은 commit·push·정본 문서 반영 전이다.

## 10. 현재 우리가 내린 제한적인 결론

1. A*, Dijkstra, D* Lite는 전역 경로를 고르는 계층이다.
2. PP와 RPP는 주어진 경로를 따라가는 계층이다.
3. DWA와 DWB는 짧은 시간의 속도·궤적 후보를 고르는 계층이며, 의미 있는 지역 우회 경로를 항상 스스로 생성한다고 볼 수 없다.
4. 곧은 기준 경로가 느린 같은 방향 Actor를 관통할 때, 안전한 옆 회전 후보가 있어도 DWB critic은 추종·감속·정지를 더 선호할 수 있다.
5. 외부 지역 reference와 단계별 waypoint를 제공하자 실제 0.2217m 이탈은 발생했다.
6. 아직 추월·재합류·도착은 증명하지 못했으므로 현재 구조의 성공을 선언할 수 없다.
7. DWA/DWB 계열을 폐기할 근거도 아직 없다. 현재 문제는 `지역 우회 경로 생성`, `reference와 critic의 역할`, `관측 신뢰도`, `장시간 계산`, `평가 증거`가 얽힌 구조 문제일 수 있다.
8. Python DWB는 기능 검증용 reference로는 쓸 수 있지만 현재 속도로 실제 runtime에 사용할 수 없다. 기능 구조가 증명되기 전에 C++·Cython·ROS2 이식부터 하는 것은 재작업 위험이 크다.
